## 1. 문서의 목적과 운영 원칙

이 문서는 Idle Clicker를 데모가 아닌 상용 모바일 게임으로 완성하기 위한 단일 기준 문서다. 기능 요청, 밸런스 변경, 시각 자산, 배포와 운영의 우선순위는 이 문서와 연결된 GitHub 이슈를 기준으로 판단한다.

1인 개발사 운영 원칙은 다음과 같다.

1. **작게 만들고 실제 기기에서 검증한다.** 문서상 완료는 완료가 아니다. Android와 iOS에서 확인한 뒤에만 완료 처리한다.
2. **핵심 재미를 먼저 완성한다.** 새 기능보다 첫 10분의 전투, 성장, 보상, 환생 경험을 우선한다.
3. **출시 기준을 초기에 적용한다.** 저장, 개인정보, 크래시, 스토어 메타데이터는 마지막 주의 작업이 아니다.
4. **모든 변경은 되돌릴 수 있어야 한다.** 밸런스 수치는 설정으로 관리하고, 세이브 형식에는 버전과 마이그레이션 전략을 둔다.
5. **한 이슈에는 한 결과물만 둔다.** 완료 조건이 분명하고, 가능한 한 한 번의 테스트 빌드로 검증할 수 있는 크기로 나눈다.

## 2. 제품 정의

### 비전

회사/조직 성장이라는 세계관에서 건물을 공략하고 인력을 채용해 생산성을 키우는 세로형 방치 클리커 게임을 만든다. 플레이어는 짧은 세션에서도 즉시 성장 보상을 느끼고, 장기적으로는 직원 조합·아티팩트·환생을 통해 새로운 성장 루프를 연다.

### 핵심 플레이 루프

1. 건물을 탭해 피해와 골드를 획득한다.
2. 골드로 탭 공격, 자동 공격, 치명타, 골드 효율을 높인다.
3. 직원을 채용·육성해 자동 DPS와 조직 시너지를 만든다.
4. 스테이지와 제한시간 보스를 돌파해 주식과 다음 구간을 연다.
5. 주식으로 아티팩트를 획득해 장기 효율을 높인다.
6. 환생으로 Beans를 얻고 영구 성장에 투자해 더 빠른 다음 회차를 시작한다.

### 출시 MVP 범위

정식 1.0에 반드시 포함할 범위다.

- 세로 화면 중심의 모바일 터치 조작과 안전 영역 대응
- 탭/자동 공격, 치명타, 스킬, 일반 적과 보스전
- 직원 채용·일괄 구매·시너지·배지 성장
- 골드, 주식, 아티팩트, 환생, Beans 영구 업그레이드
- 로컬 저장, 앱 재실행, 오프라인 보상 및 세이브 마이그레이션
- 튜토리얼, 설정(소리·진동·데이터 초기화), 접근성 옵션
- 한국어 우선 UI와 출시용 영문 스토어 메타데이터
- Android / iOS 실기기 테스트와 스토어 제출 자산

### 1.0 이후로 미루는 범위

출시 일정을 지키기 위해 아래 항목은 1.0 범위에서 제외한다.

- 실시간 멀티플레이, 길드, 랭킹
- 계정 로그인과 클라우드 동기화
- 라이브 PvP, 광고 네트워크, 결제 상품의 대규모 확장
- 수십 종의 신규 부서/이벤트를 한 번에 추가하는 콘텐츠 확장

## 3. 기술 및 품질 기준

### 기술 방향

- 게임 엔진: Phaser 3
- 웹 빌드: Vite + TypeScript
- 모바일 컨테이너: Capacitor로 기존 `dist` 빌드를 Android/iOS 프로젝트에 동기화
- 게임 내 전투 연출: Phaser 트윈, 파티클, 사운드
- HTML 기반 메뉴/온보딩/보조 UI: Motion 또는 Anime.js를 선택적으로 사용
- 저장: 로컬 저장을 유지하되 버전 필드와 마이그레이션을 추가
- 자동화: TypeScript 빌드, 브라우저 회귀 확인, 실제 기기 수동 검증

Motion과 Anime.js는 같은 장면에 중복 적용하지 않는다. Canvas 안의 게임 오브젝트는 Phaser가 소유하고, DOM UI의 전환/피드백은 Motion 또는 Anime.js가 소유한다.

### 출시 전 품질 기준

- `npm run build`가 경고 외 오류 없이 통과한다.
- 지원하는 실기기에서 첫 실행, 30분 플레이, 백그라운드 복귀, 재설치 후 동작을 확인한다.
- 세이브 손상·마이그레이션 실패 시 앱이 크래시하지 않고 안전한 초기 상태 또는 복구 안내를 제공한다.
- 화면 회전 정책, 노치/안전 영역, 작은 화면과 큰 화면에서 UI가 잘리지 않는다.
- 콘솔에 반복 오류나 디버그 로그가 남지 않는다.
- 사운드·진동·애니메이션을 끌 수 있고, 시스템의 모션 감소 설정을 존중한다.

## 4. 출시 및 사업 준비

### 배포 전략

1. Android 내부 테스트로 설치·저장·성능·크래시를 먼저 검증한다.
2. iOS TestFlight로 기기·안전 영역·심사 정보·결제 흐름을 검증한다.
3. 제한된 테스터 대상의 소프트런치에서 초반 이탈, 성장 속도, 보스 난이도, 환생 시점을 점검한다.
4. 기준을 만족한 빌드만 정식 출시한다.

### 스토어 제출 준비물

- 고유한 앱 이름, 패키지/번들 ID, 연령 등급, 카테고리
- 앱 아이콘, 런치 화면, 기기별 스크린샷, 프로모션 문구
- 한국어 설명과 영문 기본 설명, 지원 이메일, 개인정보 처리방침 URL
- 데이터 수집 여부와 제3자 SDK 목록
- 앱 심사용 빌드, 테스트 계정이 필요한 경우의 접근 정보, 심사 메모
- 이용 약관, 고객 지원 및 장애 대응 연락처

### 수익화 원칙

수익화는 핵심 루프가 실기기에서 재미있다고 검증된 뒤에만 구현한다. 도입 전에는 구매 대상, 가격, 환불, 소모/비소모 구분, 플랫폼 수수료, 확률형 요소 고지, 지역별 법적 요구 사항을 별도 이슈로 결정한다. 1.0은 결제 없이도 완결된 재미를 제공해야 한다.

## 5. 측정과 운영

출시 이전에는 분석 이벤트 설계만 하고, 개인정보 고지와 동의 방식이 확정된 뒤에 SDK를 넣는다.

최소 이벤트:

- 첫 실행, 튜토리얼 시작/완료, 첫 직원 채용
- 스테이지 진입/실패/보스 승리
- 업그레이드·아티팩트·환생 사용
- 세이브 로드/실패, 오프라인 보상 수령
- 앱 크래시, 성능 경고, 설정 변경

매 빌드에서 확인할 지표:

- 첫 세션에서 첫 직원까지 걸린 시간
- 첫 보스 도달/실패/승리 비율
- 환생 도달 시간과 환생 후 재진입률
- 세이브 실패·크래시·기기별 성능 문제
- 테스터 피드백에서 반복되는 혼란 지점

## 6. 단계별 실행 백로그

각 항목은 GitHub 이슈로 관리한다. 이슈 제목의 순서는 우선순위이며, 다음 단계의 시작 조건은 이전 단계의 완료 기준 충족이다.

### Phase 0 — 제품 기반과 의사결정

- `P0-01` 제품 기획서·용어집·MVP 범위 확정
- `P0-02` 코드베이스 건강성 정리 및 개발 표준 수립
- `P0-03` 모바일 패키징 아키텍처와 식별자 결정
- `P0-04` 아트·UX 디자인 시스템과 자산 제작 계획
- `P0-05` 개인정보·수익화·스토어 계정 준비 계획

**완료 게이트:** 출시 MVP가 문서화되고, 코드 구조와 모바일 전환 경로가 확정되며, 추가 기능 요청을 판단할 기준이 생긴다.

### Phase 1 — 플레이 가능한 버티컬 슬라이스

- `P1-01` 핵심 전투 피드백과 첫 10분 경험 완성
- `P1-02` 직원 성장·경제·보스 난이도 밸런싱
- `P1-03` 모바일 UI, 온보딩, 설정 및 접근성 구현
- `P1-04` 세이브 버전·오프라인 보상·복구 안정화
- `P1-05` 사운드·진동·시각 연출 완성

**완료 게이트:** 처음 설치한 사용자가 안내 없이 첫 보스를 처치하고, 자동 성장과 환생의 가치를 이해하며, 앱을 재시작해도 진행도가 안전하게 유지된다.

### Phase 2 — 네이티브 앱과 검증 체계

- `P2-01` Capacitor Android/iOS 프로젝트 생성 및 앱 생명주기 대응
- `P2-02` 분석·크래시 보고·개인정보 동의 설계 및 적용
- `P2-03` 자동 빌드·브라우저 회귀·실기기 QA 체크리스트 구축
- `P2-04` 성능·배터리·메모리·오프라인 환경 최적화

**완료 게이트:** 두 플랫폼에서 재현 가능한 테스트 빌드를 만들 수 있고, 치명적인 오류와 이탈 지점을 관찰할 수 있다.

### Phase 3 — 베타와 스토어 준비

- `P3-01` Android 내부/비공개 테스트 운영
- `P3-02` iOS TestFlight 운영
- `P3-03` 스토어 자산·메타데이터·개인정보 처리방침 완성
- `P3-04` 소프트런치 피드백 반영과 출시 밸런스 고정
- `P3-05` 릴리스 후보(RC)와 심사 제출 준비

**완료 게이트:** 스토어 제출 정보가 완전하고, 실제 테스터의 치명적 문제와 경제 밸런스 문제가 해결됐으며, RC가 정해진 기기 범위를 통과한다.

### Phase 4 — 정식 출시와 운영

- `P4-01` Google Play/App Store 정식 제출과 출시 확인
- `P4-02` 출시 후 7일 운영, 장애 대응, 피드백 분류
- `P4-03` 1.1 업데이트 백로그와 장기 운영 계획 수립

**완료 게이트:** 출시 상태·크래시·사용자 피드백을 매일 확인하고, 다음 업데이트의 우선순위가 데이터와 피드백으로 정해진다.

## 8. 릴리스 의사결정 게이트

| 게이트 | 통과 조건 | 통과하지 못하면 |
| --- | --- | --- |
| MVP 승인 | 핵심 루프와 1.0 제외 범위가 합의됨 | 새 기능 구현을 시작하지 않음 |
| 버티컬 슬라이스 | 첫 10분과 저장/복귀가 실기기에서 자연스러움 | 콘텐츠 확장보다 UX·밸런스 수정 |
| 베타 진입 | Android/iOS 테스트 빌드와 피드백 수집 경로 존재 | 스토어 자산 제작을 보류 |
| RC 승인 | 치명적 버그 0건, 스토어 정보 완성, 실기기 체크 통과 | 제출하지 않고 수정 빌드 생성 |
| 출시 유지 | 크래시/저장 문제를 모니터링하고 대응 가능 | 기능 개발보다 안정화 우선 |

## 9. 1인 개발사 주간 리듬

- 월요일: 이번 주 이슈를 하나의 사용자 가치 단위로 확정한다.
- 화요일~목요일: 구현, 로컬 빌드, 실제 기기 확인을 반복한다.
- 금요일: 회귀 확인, 이슈 정리, 다음 주 우선순위를 결정한다.
- 매 작업 종료: 변경 요약, 검증 결과, 남은 위험을 GitHub 이슈/PR에 기록한다.

기능을 병렬로 많이 시작하지 않는다. `진행 중` 이슈는 원칙적으로 하나만 두고, 막혔을 때만 다음 독립 이슈로 이동한다.
