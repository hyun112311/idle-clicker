# 기술 기준선

> 적용 이슈: P0-02 코드베이스 건강성 정리 및 개발 표준 수립

## 모듈 책임

| 모듈 | 책임 | 맡지 않는 책임 |
| --- | --- | --- |
| `GameScene` | 게임 루프, 씬 생명주기, 매니저 조립, 전투 이벤트 조율 | 영구 상태 계산, UI 레이아웃 세부 구현 |
| `UpgradeManager` | 골드·스탯·직원·환생·아티팩트의 단일 상태와 계산 | 직접적인 화면 표시, 브라우저 저장소 접근 |
| `UIManager` | 화면 표시, 입력 전달, 접근성/설정 UI | 경제·전투 규칙, 다른 앱 데이터 삭제 |
| `SaveManager` | 게임 세이브 저장·로드·마이그레이션·오프라인 보상 | UI 구현, 밸런스 계산 |
| `Building` | 적 체력, 피격, 생성, 사망 연출 | 스테이지 진행과 보상 지급 |
| `config/GameConfig` | 게임 밸런스와 저장 정책 상수 | Phaser 렌더링 설정 |
| `GameConfig` | Phaser 런타임 설정 (`PhaserGameConfig`) | 게임 밸런스 |

## 세이브 계약

- 저장 데이터는 `version` 필드를 반드시 가진다.
- 새 필드는 이전 세이브를 읽을 수 있도록 기본값을 제공한다.
- 지원하지 않는 미래 버전 또는 구조가 아닌 데이터는 로드하지 않고 앱이 안전한 초기 상태를 유지한다.
- 수치형 데이터는 유한한 값과 허용 범위를 검증한 뒤에만 상태에 반영한다.
- 오프라인 보상은 비정상적인 기기 시간으로 무한히 늘어나지 않도록 상한을 둔다.
- 데이터 초기화는 `idle_clicker_save` 키만 삭제한다. `localStorage.clear()`는 사용하지 않는다.

## 변경 규칙

1. 밸런스 값은 로직 코드에 상수로 추가하지 않고 게임 설정에 둔다.
2. UI는 상태를 직접 수정하지 않고 명시적인 콜백/매니저 메서드를 사용한다.
3. 자동 공격·저장 같은 반복 경로에는 디버그 로그를 남기지 않는다.
4. 상태·세이브 형식을 바꾸면 신규 세이브, 이전 세이브, 손상 세이브, 앱 재시작을 확인한다.
5. 모든 기능 변경은 `npm run build`를 통과해야 하며, 핵심 흐름은 브라우저 또는 실기기에서 확인한다.

## 현재 최소 검증 흐름

1. 새 게임 시작 후 탭 공격과 첫 구매를 확인한다.
2. 직원 채용, 자동 공격, 보스 진입/승리를 확인한다.
3. 환생 후 영구 재화와 초기화 범위를 확인한다.
4. 앱을 종료·재실행해 저장과 오프라인 보상을 확인한다.
5. 부분 필드만 가진 이전 세이브와 손상된 세이브에서 앱이 크래시하지 않는지 확인한다.

## 다음 정리 대상

- `UIManager`와 `UpgradeManager`를 기능 단위로 더 작은 컴포넌트로 분리한다.
- 세이브 실패 시 사용자에게 복구/초기화 선택지를 제공한다.
- 브라우저 회귀 시나리오와 실기기 QA를 자동화한다.
- 네이티브 앱 전환 전에 화면 크기·안전 영역·백그라운드 생명주기를 시험한다.
